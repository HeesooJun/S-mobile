# Jira

프로젝트 관리를 위한 협업 툴

작업의 진행 상황을 추적하여 프로젝트 관리에 도움

## 지라 기본 구성 요소

1. 프로젝트
- 가장 상위 단위로 특정 목표를 달성하기 위한 작업 그룹
- 프로젝트를 구성하는 이슈와 이슈를 시각적으로 파악할 수 있는 보드로 구성

2. 이슈
- 모든 작업의 기본 단위
- 하나의 작업, 버그, 개선 사항 등 

3. 보드
- 프로젝트의 이슈들을 시각적으로 표현하는 공간
- 보드를 통해 프로젝트의 모든 이슈와 상태를 실시간으로 확인
- 캘린더, 칸반, 타임라인, 목록 등 형식



## 작업 유형
1. Epic
- 큰 틀의 프로젝트나 목표

2. Story / Task
- 에픽을 달성하기 위한 개별 이슈들

3. Sub-task
- Story나 Task를 완료하기 위해 쪼개진 구체적 실행 단계


## 이슈 필드
1. 스토리 포인트
- 업무의 상대적 크기 (시간 아님)
- 업무량, 복잡도, 불확실성 등을 고려
- 피보나치 수열 1,2,3,5,8 으로 점수 부여

2. 우선순위
- 작업의 처리 순서 결정
- 비즈니스 가치, 긴급성, 의존성 고려
- 팀 내에서 점수 기준점에 대한 합의가 중요


## 팀 컨벤션

### 1. 이슈 구조

- Epic: 도메인별 프로젝트 또는 큰 모듈
    - 예: `[FE] 사용자 앱`, `[AI] 재난 감지 모델링`, `[NET] 통신 구현`
- Story: 해당 도메인에서 완료해야 할 기능 개발 단위
    - 예: `[FE] SOS UI`, `[NET] BLE 통신 연결`
- Sub-task: 스토리를 완료하기 위한 세부 구현 단계

### 2. 작성 규칙

**2.1 Epic 작성 규칙**
에픽 이름 앞에 도메인을 명시하여 구분을 확실히 합니다.

- 형식: `[도메인] 프로젝트명/모듈명`
- 예시:
    - `[FE] 대국민 재난 알림 앱`
    - `[AI] 재난 상황 감지 모델`
    - `[NET] 데이터 수집 및 API 서버`
    - 
    

**2.2 Story 작성 규칙**
스토리는 이제 **특정 도메인의 작업**이므로, 타 도메인의 내용을 포함하지 않습니다.

- 형식: `구체적인 기능/개발 단위` (말머리 생략 가능, 에픽으로 구분이 되므로)
- 예시 (FE Epic 하위): `로그인 페이지 UI 구현`
- 예시 (NET Epic 하위): `회원가입 API 개발`
- 예시 (AI Epic 하위): `YOLOv8 모델 학습 데이터셋 구축`

**2.3 Sub-task 작성 규칙**

- 형식: `세부 작업 내용`
- 예시 (Story: 로그인 페이지 UI 구현 하위):
    - `레이아웃 퍼블리싱`
    - `유효성 검사 로직 작성`
    - `Axios 연동`

### 3. 예시 시나리오

하나의 기능(화재 감지)을 개발하더라도, 에픽이 나뉘어 있으므로 **Story가** 각각 생성됨

- **Epic: `[AI] 재난 상황 감지 모델`**
    - **Story:** `화재 감지 모델 학습 및 최적화`
        - Sub-task: `화재 데이터셋 라벨링`
        - Sub-task: `모델 학습 및 mAP 측정`
        - Sub-task: `tflite 모델 변환`
- **Epic: `[NET] 데이터 수집 및 API 서버`**
    - **Story:** `감지 데이터 수신 소켓 서버 구현`
        - Sub-task: `Socket.io 서버 설정`
        - Sub-task: `수신 데이터 파싱 및 DB 저장`
- **Epic: `[FE] 대국민 재난 알림 앱`**
    - **Story:** `실시간 화재 알림 수신 기능`
        - Sub-task: `FCM(Firebase) 설정`
        - Sub-task: `알림 수신 시 팝업 UI 개발`

### 4. 스토리

#### 4.1 스토리 포인트

- 작업의 규모와 복잡도를 표현
- 피보나치 수열 1,2,3,5,8 을 사용
- Story에 부여
- 도메인 내에서 상대적인 크기 (AI의 3과 FE의 3이 다를 수 있음)

#### 예시

- **1 SP (매우 쉬움)**
    - 단순 텍스트 변경, 버타(오타) 수정, 설정 값 변경.
    - 고민 없이 바로 처리 가능 (0.5일 미만).
- **2 SP (쉬움 / 기본)**
    - 루틴한 작업. 익숙한 패턴의 API 생성, 단순 UI 컴포넌트 개발.
    - 불확실성 없음 (0.5일 ~ 1일).
- **3 SP (보통)**
    - 약간의 로직 고민 필요. 외부 라이브러리 연동, 데이터 전처리 로직.
    - 일반적인 기능 개발 단위 (1일 ~ 2일).
- **5 SP (어려움 / 복잡함)**
    - 리서치가 필요하거나 로직이 복잡함. 새로운 모델 아키텍처 도입.
    - 예상치 못한 변수가 있을 수 있음 (3일 ~ 1주일).
- **8 SP 이상**
    - **경고:** 하나의 스토리로 처리하기엔 너무 큽니다.
    - **행동:** 반드시 스토리를 2개 이상으로 쪼개세요. (예: `로그인 구현` -> `UI 구현` / `API 연동` / `예외 처리`)

#### 4.2 우선순위

비즈니스 가치와 긴급성을 기준으로 4단계로 나눔

- **Highest (최상 / P1) - 지금 당장**
    - **긴급:** 서버 다운, 핵심 기능(로그인, 결제, 메인 모델 추론) 작동 불가.
    - **블로커:** 이 작업이 안 되면 다른 파트(FE/AI/NET)가 일을 못 함.
    - *이번 스프린트 최우선 처리.*
- **High (상 / P2) - 이번 스프린트 필수**
    - 주요 비즈니스 기능. 프로젝트의 핵심 목표.
    - *반드시 이번 스프린트 내에 완료해야 함.*
- **Medium (중 / P3) - 보통**
    - 일반적인 기능. 있으면 좋은 기능.
    - *시간이 부족하면 다음 스프린트로 넘길 수 있음.*
- **Low (하 / P4) - 나중에 / 틈날 때**
    - 사소한 UI 디테일 수정, 코드 리팩토링, 주석 정리.
    - *여유 있을 때 처리.*
