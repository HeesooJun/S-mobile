# 레포 구조와 개발 규칙 정리

지금 레포는 기본 구조 상태라서, 처음엔 MVVM으로 갈까 생각했다. 근데 프로젝트가 오프라인 재난 상황 + 실시간 하드웨어 제어라서, 화면 상태 관리보다 센서/통신 이벤트를 최대한 빨리 흘려보내는 게 더 중요하다고 봤다. 그래서 Activity 중심의 전통적인 패턴(MVC 변형)으로 정리했다.

## 아키텍처 선택 배경 (MVVM 대신 Activity 중심)

처음엔 MVVM 장점(역할 분리/테스트)을 떠올렸다. 그런데 BLE/UWB/센서/음성 데이터는 지연에 민감해서, ViewModel/Observer 체인으로 한 번 더 도는 게 아쉬웠다. 콜백이 들어오면 Activity에서 바로 처리하는 게 딜레이가 덜하다고 판단했다.

또 센서 등록/해제, 블루투스 스캔, 마이크 권한 같은 건 Activity 생명주기랑 붙어 있어서, 화면이 직접 관리하는 게 더 안전했다. ViewModel에 넣으면 Context가 필요해져서 애매해지고, 구조가 커질수록 누수 위험도 늘어난다.

이 앱은 UI 상태를 보여주는 것보다 “신호 수신/송출” 이벤트가 핵심이라 이벤트 기반으로 단순하게 가는 게 맞다고 봤다. MVP 범위에서 MVVM 계층을 다 쌓는 건 과했고, 흐름이 단순해야 문제 찾기도 빨랐다.

## 폴더 구조(Activity 중심, 적용 예정)

- ui: Activity/Fragment, 화면 UI
- core: BLE/UWB/센서/음성 트리거 같은 하드웨어 제어
- data: 로컬 저장소, 모델
- common/util: 공통 유틸

## 코딩 컨벤션

개발 경험이 적은 팀원도 있어서, 코드 품질과 일관성을 지키려면 규칙이 꼭 필요하다고 생각했다. 그래서 최소한의 규칙을 먼저 정하고, 도구로 자동화하는 방향으로 맞췄다.

- Kotlin 클래스/파일: PascalCase
- 함수/변수: camelCase
- 패키지: 소문자
- 리소스: snake_case
- 품질 관리 도구: ktlint + detekt + EditorConfig

## 브랜치 전략

충돌과 실수를 줄이기 위해 브랜치 흐름을 단순하게 가져가기로 했다. 작업은 develop에서 분기하고, 안정성은 main에서 보장하는 구조다.

- main: 항상 안정
- develop: 통합 브랜치
- feature/*, fix/*, chore/*: develop에서 분기
- PR은 develop으로, 머지 후 브랜치 삭제
