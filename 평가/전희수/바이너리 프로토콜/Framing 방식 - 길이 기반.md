# Framing 방식 - 길이 기반

처음에는 “이렇게 복잡해야 하나?” 싶었는데, 정리하다 보니 **이 구조가 필수라는 걸 깨달음.**  
BLE는 제약이 많아서 **길이 기반 헤더 + 릴레이 제어 + 중복 제거**가 없으면 실제 환경에서 버티기 어렵다.

---

## 1) 왜 길이 기반 바이너리 구조인가?
BLE 환경은 아래 문제가 있습니다.
- **한 번에 보낼 수 있는 크기가 작음(MTU 제한)**  
  → 메시지는 잘리거나, 애초에 쪼개서 보내야 함
- **순서/재전송/중복이 발생**  
  → 같은 메시지가 여러 경로로 들어올 수 있음
- **텍스트 구분자(STX/ETX)는 위험**  
  → 본문에 같은 문자가 들어가면 프레임 경계가 깨짐

그래서 **“길이 기반 바이너리 패킷”**이 필요합니다.  
헤더에 **페이로드 길이**가 있으면 수신자는 “정확히 이 길이만큼” 읽고 끝낼 수 있습니다.  
즉, **프레임 경계(메시지의 시작/끝)를 숫자로 고정**하는 방식입니다.

---

## 1-1) 길이 기반 패킷 “겉모습” 예시
아래는 **헤더/바디를 구분해서** 패킷 흐름을 한 줄씩 풀어쓴 겁니다. (바이트 포함)

**[헤더 Header]**
- **Version (1 byte)**: 이 패킷을 어떤 버전 규칙으로 읽어야 하는지 알려줌
- **Type (1 byte)**: 메시지 종류(일반/암호화/조각 등)를 구분
- **TTL (1 byte)**: 이 패킷이 몇 번까지 중계될지 제한
- **Timestamp (8 bytes)**: 중복 제거/재전송 판단에 쓰는 시간 정보
- **Flags (1 byte)**: “옵션 필드가 있는지”만 표시하는 스위치
- **Length (v1=2 bytes / v2=4 bytes)**: Payload가 몇 바이트인지 정확히 알려줌

**[바디 Body]**
- **SenderID (8 bytes)**: 누가 보냈는지 (발신자)
- **RecipientID (옵션, 8 bytes)**: 누구에게 보내는지 (1:1일 때만)
- **Payload (Length만큼)**: 실제 내용
- **Signature (옵션, 64 bytes)**: 위조 방지를 위한 서명

**읽는 순서(중요):**
1) 헤더를 먼저 읽는다  
2) Length를 보고 “Payload를 몇 바이트 읽어야 하는지”를 안다  
3) 옵션 필드는 Flags로 “있다/없다”를 판단한다  

**즉, 구분자(STX/ETX)가 없어도 정확히 끊어 읽을 수 있음.**

추가로 꼭 기억할 점:
- **총 크기는 고정(128바이트 같은 것) 아님**  
- **Payload 길이에 따라 매번 달라짐 = 가변 길이**  
- 그래서 “길이 기반”이라는 말은 **‘가변 길이를 헤더 길이 값으로 정확히 잘라 읽는다’**는 뜻임

간단히 쓰면 이렇게 이해하면 됨:
```
총크기 = 헤더(13/15) + SenderID(8) + RecipientID(옵션,8) + Payload(Length) + Signature(옵션,64) + Route(옵션)
```

## 2) 패킷에 왜 이런 필드가 들어가나?
아래는 패킷 필드와 그 **필요한 이유**입니다.

### 버전 (Version)
- **왜 필요?** 프로토콜이 확장될 때 구버전/신버전이 섞일 수 있음
- **효과**: 수신 측이 “이 버전은 이렇게 읽어라”를 판단
- **없으면?** 새로운 필드가 추가될 때 구버전 앱이 전부 깨짐

### 타입 (Type)
- **왜 필요?** 메시지 종류에 따라 처리 로직이 완전히 다름
- **예시**: 일반 메시지 / 핸드셰이크 / 조각(Fragment) 등
- **효과**: 수신 측이 어떤 처리기를 쓸지 즉시 결정
- **없으면?** 모든 메시지를 같은 방식으로 해석하다가 오류 발생

### TTL (Time-To-Live)
- **왜 필요?** 메시가 중계되면 무한 루프 가능
- **효과**: 릴레이할 때마다 TTL-1, 0이면 중계 중단
- **추가 효과**: TTL이 높으면 “직접 이웃”인지 판단 가능
- **없으면?** 메시지가 계속 돌면서 배터리/트래픽 폭주

### 타임스탬프 (Timestamp)
- **왜 필요?** 중복 제거/재전송/리플레이 공격 방지
- **효과**: “이 메시지는 너무 오래됨” 판단 가능
- **없으면?** 오래된 메시지가 계속 재등장하거나, 공격에 취약

### 플래그 (Flags)
- **왜 필요?** 모든 패킷이 똑같이 크면 낭비
- **효과**: 수신자/서명/압축/라우트 존재 여부만 표시해서 효율화
- **없으면?** “있는지 없는지”를 매번 추측해야 해서 파싱이 불안정

### 페이로드 길이 (Payload Length)
- **왜 필요?** 정확한 경계 분리
- **효과**: 구분자 없이도 안정적으로 패킷 파싱 가능
- **없으면?** 수신 측이 ‘어디까지가 한 메시지인지’ 모름

### SenderID (발신자 ID)
- **왜 필요?** 누가 보냈는지 알아야 중복 제거/암호화/표시가 가능
- **효과**: 네트워크 상태나 사용자 표시에도 사용
- **없으면?** “누가 보냈는지” 몰라서 중복 제거/대상 처리 불가

### RecipientID (수신자 ID, 선택)
- **왜 필요?** 브로드캐스트인지 1:1인지 구분
- **효과**: 내가 처리할 메시지인지, 릴레이할지 판단
- **없으면?** 모든 메시지를 전부 처리/릴레이하는 비효율 발생

### Payload (본문 데이터)
- **왜 필요?** 실제 전달 내용
- **효과**: 텍스트, 음성, 명령, 센서 데이터 등 자유롭게 담을 수 있음
- **없으면?** 헤더만 있고 전달할 실질 데이터가 없음

### Signature (서명, 선택)
- **왜 필요?** “진짜 그 사람이 보낸 메시지인지” 확인
- **효과**: 위조/스푸핑 방지, 신뢰성 확보
- **없으면?** 아무나 다른 사람인 척 메시지를 보낼 수 있음

### Route (라우트, 선택)
- **왜 필요?** 네트워크가 커지면 무작정 브로드캐스트는 비효율
- **효과**: 특정 경로로만 전달해 트래픽 감소
- **없으면?** 항상 전체 브로드캐스트 → 대규모 네트워크에서 부담

## 3) Message ID는 왜 필요한가?
메시지 ID는 **중복 제거와 상태 추적**의 핵심입니다.

- **중복 제거(dedup)**: 여러 경로로 동일 메시지가 들어올 수 있음
- **읽음/전달 확인**: “이 메시지는 읽혔다/전달됐다”를 추적
- **재전송**: 상대가 잠시 오프라인이어도 재전송 가능

실제 구현에서는 보통 다음 2층 구조를 씁니다.
- **패킷 레벨 ID**: 중복 패킷 제거용
- **메시지 레벨 ID**: 사용자 메시지의 전달/읽음 상태 추적용

초보자 관점 비유:
- **패킷 ID** = “택배 박스 자체의 일련번호”  
- **메시지 ID** = “그 박스 안 문서의 문서번호”  
같은 메시지가 여러 박스로 와도 **문서번호로 한 번만 처리**할 수 있음

---

## 4) Fragment(조각) 처리가 왜 필요한가?
BLE는 한 번에 보낼 수 있는 크기가 작습니다.
- **큰 데이터(음성/파일)** → 여러 조각으로 나눠야 함
- **수신 측**은 모든 조각이 모이면 **재조립**
- 일부가 누락되면 **시간 제한 후 폐기**

즉, “조각화 + 재조립”이 필수입니다.

조각화가 있다는 말은 보통 이런 정보가 함께 필요하다는 뜻입니다.
- **조각 ID**: 이 조각이 어떤 원본 메시지에 속하는지
- **조각 번호 / 전체 개수**: 몇 번째 조각인지, 총 몇 개인지
- **타임아웃**: 일정 시간 내에 다 못 받으면 폐기

---

## 5) TTL + 릴레이는 왜 중요할까?
메시 네트워크의 핵심은 **“내가 직접 연결된 사람이 아니어도 전달 가능”**입니다.
- 릴레이가 없으면 **거리 제한**이 매우 큼
- TTL이 없으면 **폭주/루프** 발생

즉, **릴레이는 필수지만, TTL로 제한해야 안전**합니다.

또 한 가지 포인트:
- **네트워크가 커질수록 무조건 릴레이는 부담**  
  그래서 TTL이나 확률 기반 릴레이를 써서 **트래픽을 줄이는 전략**이 필요합니다.

---

## 6) 압축과 패딩이 왜 들어가나?
- **압축**: 긴 메시지나 파일의 전송 시간을 줄이기 위함
- **패딩**: 패킷 길이만 보고 메시지 종류를 추측하는 공격(트래픽 분석) 완화

추가 설명:
- **압축은 작은 메시지엔 손해**일 수 있음 (헤더 + CPU 비용 때문에)  
  → 보통 “크기가 일정 이상일 때만 압축”하는 조건을 둠
- **패딩은 일부러 길이를 맞추는 것**  
  → 공격자가 “이 길이면 파일이겠네”라고 추측하는 걸 방지

---

## 7) 전체 흐름 (간단 버전)
1. 메시지 생성
2. 패킷 헤더 구성(버전/타입/TTL/길이 등)
3. 필요 시 암호화/압축
4. MTU 초과 시 조각화
5. BLE로 전송
6. 수신 측은 길이 기반으로 파싱
7. 중복 제거 + TTL 검사
8. 내 메시지면 처리, 아니면 TTL-1 후 릴레이

조금 더 현실적인 흐름으로 풀어보면:
1) **메시지 ID 생성**  
2) **필요하면 암호화(Noise)**  
3) **헤더+본문 조합 → 패킷 인코딩**  
4) **MTU보다 크면 조각화 후 전송**  
5) **수신 → 재조립 → 중복 제거 → 처리 or 릴레이**

## 한 줄 요약
**이 구조는 “작은 MTU + 중복/루프 + 보안” 문제를 동시에 해결하기 위한 설계다.**

## 개인 요약 (깨달은 점)
이렇게 정리하고 보니 **왜 이 구조가 필요한지** 확실히 알겠음.  
BLE 환경은 불안정하고 제한이 많아서, **길이 기반 헤더·TTL·중복 제거·조각화**가 없으면
메시지가 금방 깨지거나 무한 루프가 생길 수밖에 없다.  
그래서 이런 방식으로 설계하는 게 **현실적으로 가장 안전하고 확장하기 좋은 선택**이다.
